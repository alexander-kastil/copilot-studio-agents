# Live sources and uploaded files
### Why grounding matters for information that moves
- An **uploaded file** is an indexed copy: the agent knows what you uploaded last
- An **IQ connection** reads the source where it lives when the question arrives
- That matters for information that moves, such as a **customer email from this morning**
- You change a file by uploading a new version; an IQ source is tuned by its **owner**

# Building apps
### Describe the app, then review and refine it until the main scenarios work
- **Describe**: name the outcome, people, data and actions; Copilot Studio generates the data model, logic and interface
- **Refine**: one small change per message, checked in the live preview; the code view is read-only
- **Data access**: granted on the SharePoint list or Dataverse table, separately from sharing the app

# Evaluating agents with test sets
### Fill a set, run it, change one thing, run it again
- **Test set**: conversations of user questions with optional expected responses, filled by Quick conversation set, CSV upload or by hand
- **General quality**: the one test method on the Evaluate tab; it judges relevance and completeness and does not compare to the expected response
- **User profile**: the identity a run executes as, matched to the access real users have
- **Invalid and Error**: about the run or the case, so clear them before reading Pass and Fail
- **One change per run**: baseline, one change, re-run the same set, compare the cases that flipped

# A test set worth trusting
### Weight the cases toward where the agent is likely to fail
- **Grounded facts**: the agent reports something from its knowledge correctly
- **Guardrails**: it refuses what it should, such as a binding price quote
- **Off-topic**: it declines instead of answering from general model knowledge
- **Multi-turn**: it holds context and asks for the missing detail

# From a failing case to a fix
### What went wrong names the component to change
- **Wrong or missing fact**: fix the knowledge source
- **Refused too little or too much**: fix the instructions
- **Wrong tool or no tool**: fix the tool description
- **Lost the thread across turns**: fix the multi-turn design, then re-run the same set

# Takeaways
### What to carry into publishing and maintaining
- Decide the **kind of agent** before you build: there is no conversion
- Read the **step list** and **History** to see how the orchestrator planned
- A skill's **description** and an MCP server's **description** decide when they are used
- Prove grounding in the **activity trace**, not in the wording of the reply
- Run the **same test set** before and after every change
